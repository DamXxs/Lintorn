🥽 Vision Hardware — Matorn Extended (projet secondaire)
🥽 Hey Matorn — Glasses Integration
Projet secondaire ambitieux — ne bloque pas le développement principal de Matorn
Architecture cible : App mobile compagnon (Android/iOS) → SDK Meta Wearables → Django API smart booking → Confirmation vocale + AR display
SDK Meta en developer preview depuis déc. 2025 — disponibilité publique générale prévue 2026 — Ray-Ban Meta Gen 1 & Gen 2 supportés
Concept : Le mécanicien porte ses Ray-Ban Meta. Il dit "Hey Matorn, RDV Mr Dupont vendredi 14h pour vidange" → l'app mobile capte la commande → envoie à Django → le bot analyse les dispos → propose un créneau → confirmation vocale → RDV créé dans Matorn.

Bonus caméra : Photo / vidéo d'une pièce HS envoyée directement dans la fiche véhicule client depuis les lunettes, mains libres. Preuve visuelle pour le client.
Futur AR : Avec les Ray-Ban Display (HUD — annoncé 2026), afficher le planning de la journée sous l'œil pendant les interventions.
01
Endpoint Django "Smart Booking"
Endpoint API qui reçoit une demande de RDV parsée, analyse les créneaux libres, retourne une proposition. Faisable maintenant dans Matorn — utile même sans lunettes.
faisable maintenant
02
App mobile compagnon
App Android/iOS qui parle à l'endpoint Django. Intègre le SDK Meta Wearables pour accès caméra et micro des lunettes. Photo/vidéo pièces HS → fiche véhicule.
moyen terme
03
"Hey Matorn" — Commandes vocales
Déclenchement vocal custom via SDK. Commande transcrite (speech-to-text), parsée et envoyée à Django. Retour audio dans les lunettes pour confirmer le RDV créé.
long terme
04
Planning AR sous l'œil
Avec les Ray-Ban Display (HUD — annoncés 2026), afficher le planning de la journée en AR. Le mécanicien voit ses RDV sans lâcher ses outils.

📐 Conventions & règles du projet
Architecture
3 couches : Component → Service → api.js → Django
Import direct depuis api.js dans un composant = anti-pattern
Django = source de vérité, React = affichage uniquement
Toute modale passe par Modal.jsx
Tout formulaire en modal importe forms.css
Style de code
PascalCase composants, camelCase fonctions/vars
CSS vanilla BEM — pas de framework CSS
rem/em plutôt que px (accessibilité mobile)
Commentaires en français dans le code
Fichiers complets toujours (pas de diffs partiels)
logger.js pour tous les appels API
Environnement
Docker (local PC) = tests réels backend
Codespaces = frontend + backend (API OK via URLs relatives)
REACT_APP_API_URL || '/api' — fonctionne partout
Referentiel PKs jamais dans les fixtures
